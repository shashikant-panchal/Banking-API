2. Core Technical Questions & How to Answer

Q1 Why did you separate the code into Controllers, Validators, Services, and Repositories?
Answer Script

Clean Architecture & Single Responsibility Principle (SRP):

  • Controllers (src/handlers/): Pure presentation logic. They parse HTTP requests, extract parameters, invoke validators and services, and format HTTP response envelopes (200, 201, 400, etc.). They have no database queries or business rules.
  • Validators (src/validators/): Pure validation functions. They fail fast right at the gateway boundary, rejecting malformed emails, invalid enums, negative balances, or fractional cents before hitting business logic or database layers.
  • Services (src/services/): Domain business logic. Services enforce banking rules: verifying that parent customers exist, checking accounts are OPEN, verifying currency matching, and checking for sufficient funds (409 Conflict). They are completely decoupled from HTTP status codes and AWS SDK specifics.
  • Repositories (src/repositories/): Data access abstraction. They encapsulate all DynamoDB commands (GetCommand, PutCommand, QueryCommand, UpdateCommand, TransactWriteCommand). This allows database schema changes or index tuning without touching business rules.
Q2 How does the JWT Authentication Middleware work across all APIs?
Answer Script

Bearer Token Guard via withAuth Higher-Order Function:

  • Every banking handler is wrapped with withAuth(handler) from src/middlewares/auth.middleware.js.
  • It inspects the Authorization: Bearer <token> header (case-insensitively).
  • If the header is missing, malformed, or has an invalid/expired token, it immediately intercepts and returns 401 Unauthorized with { error: "UNAUTHORIZED", message: "..." }.
  • Upon valid verification using jsonwebtoken and JWT_SECRET, it attaches the decoded user payload to event.user so downstream controllers and services can access caller identity.
  • I also created a dedicated endpoint POST /auth/token that generates valid signed HS256 tokens for API consumers and automated tests.

2. Core Technical Questions & How to Answer (Continued)

Q3 How did you design your DynamoDB access patterns and queries in the Repository layer?
Answer Script

Point Reads ($O(1)$) and GSI Query vs. Table Scan ($O(N)$):

  • Point Reads: Customer and Account lookups by ID use GetCommand targeting their respective partition keys (customerId, accountId) for consistent single-digit millisecond latency.
  • Querying Customer Accounts (GET /customers/{id}/accounts): In DynamoDB, the Accounts table primary key is accountId. Running a Scan with a filter expression is a major production anti-pattern because it reads the entire table, consuming unbounded Read Capacity Units (RCUs).
  • GSI Solution: In account.repository.js, I query the CustomerIdIndex Global Secondary Index using QueryCommand with KeyConditionExpression: "customerId = :customerId". This targets only the specific customer's partition in the index, achieving $O(1)$ partition isolation.
  • Repository Encapsulation: All AWS SDK commands (GetCommand, PutCommand, DeleteCommand, QueryCommand, UpdateCommand, TransactWriteCommand) reside solely in the repository layer.
Q4 How did you implement cross-account transfers and handle concurrency?
Answer Script

The Double-Spend / Partial Failure Risk: In financial transfers, if debit succeeds but credit fails (e.g., timeout or crash), funds vanish. If credit succeeds but debit fails, money is minted.

My Solution — DynamoDB ACID Transactions (TransactWriteItems):

  • In account.repository.js, I bundle the debit (SET balance = balance - :amount) and credit (SET balance = balance + :amount) into a single TransactWriteCommand. Both operations commit atomically or both roll back.
  • Optimistic Concurrency Guards: On the debit item, I enforce ConditionExpression: "balance >= :amount AND #status = :openStatus AND currency = :currency".
  • Race Condition Handling: If two transfers attempt to debit the same account concurrently, DynamoDB aborts the transaction with TransactionCanceledException. My handler catches this and returns a clean 409 Conflict.
  • Resilience Fallback: For local development environments (like dynalite) that do not support TransactWriteItems, the repository includes a resilient two-phase conditional update with compensating rollback.
Q5 How did you handle input validation and financial precision?
Answer Script
  • Dedicated Validator Layer (src/validators/): Created pure functions: validateCreateCustomer, validateCreateAccount, validateDeposit, validateWithdraw, and validateTransfer.
  • Floating-Point Precision Guard: In IEEE-754 floating-point arithmetic, fractions like 0.1 + 0.2 yield 0.30000000000000004. To prevent rounding vulnerabilities and exploits, validators strictly enforce that all monetary amounts must be finite numbers with at most 2 decimal places (cents).
  • Enum & Business Invariants: Enforce CHECKING / SAVINGS, CAD / USD, RFC 5322 regex for emails, and prevent self-transfers (fromAccountId !== toAccountId).
Q6 How did you test your implementation?
Answer Script
  • I built an automated unit test suite using Node's native node:test framework and aws-sdk-client-mock.
  • The suite contains 79 tests across 26 test suites running in ~590ms without needing live Docker containers or external network calls.
  • Each layer is tested in isolation: 6 auth tests, 18 validator tests, 10 service tests, 8 repository tests, and 37 controller tests.

4. Technical Buzzword & Architectural Concept Summary

Key concepts to mention during the interview:
• Clean Architecture & Single Responsibility: Handlers handle HTTP; Validators validate input; Services execute business logic; Repositories access DynamoDB.
• JWT Bearer Authentication: Stateless token verification via reusable withAuth middleware.
• GSI vs. Table Scan: Explain that GSI provides $O(1)$ partition isolation, whereas Scan is an $O(N)$ linear-cost anti-pattern.
• DynamoDB ACID Transactions: Emphasize all-or-nothing atomicity via TransactWriteItems.
• Optimistic Concurrency Control: Use of ConditionExpression on balances to prevent race conditions and overdrafts.
• Financial Precision: Validation of 2-decimal place limits to prevent IEEE-754 precision issues.
