1. Recruiter Feedback & Architecture Evolution

Recruiter Feedback Addressed:
"Why you are not separated, like the services, account service, transaction service, or customer service... And also make repository, mention all your queries... DynamoDB get commands, put command, delete command, queries... And validation: make a separate folder/file for validation, export functions and call operations to validate request body, parameters... Add authentication with JWT middleware in every API."

In response, the system was refactored from coupled Lambda handlers into a 4-Tier Clean Architecture separating concerns across Controllers, Middlewares, Validators, Services, and Repositories:

HTTP Request ──> JWT Auth Middleware [src/middlewares/auth.middleware.js] │ (Verifies Bearer token, attaches decoded user or throws 401) ▼ Controllers / Handlers [src/handlers/*.js] │ (Thin controllers: parse JSON, invoke validator, call service) ┌─────────┴─────────┐ ▼ ▼ Validator Layer Service Layer [src/services/*.js] [src/validators/*.js] │ (Domain business logic, financial rules, overdraft checks) (Pure functions, checks ▼ regex, 2-decimals, Repository Layer [src/repositories/*.js] returns 400 errors) │ (Encapsulates GetCommand, PutCommand, DeleteCommand, │ GSI QueryCommand, UpdateCommand, TransactWriteCommand) ▼ Amazon DynamoDB (Customers & Accounts Tables)

3. Detailed Breakdown by Architectural Layer

Layer 1 Middleware & Authentication (src/middlewares/auth.middleware.js)
  • Token Generation (generateToken): Signs JWT with payload { sub, username, role } using jsonwebtoken (HS256) and a 2-hour expiry.
  • Bearer Token Verification (authenticate): Parses Authorization: Bearer <token> header. Rejects missing, malformed, expired, or tampered tokens with 401 Unauthorized ({ error: "UNAUTHORIZED", message: "..." }).
  • Higher-Order Wrapper (withAuth): Cleanly wraps any Lambda handler function. Decodes the token, attaches event.user, and intercepts authentication errors automatically without code duplication in controllers.
Layer 2 Controllers / Handlers (src/handlers/)
  • Pure Presentation / Gateway Logic: Handlers are strictly HTTP controllers. They do not contain any database queries or business decision logic.
  • Workflow: withAuth → parseJsonBody → call Validator → call Service → return HTTP 200/201 response envelope.
  • Endpoints Handled: POST /auth/token, POST /customers, GET /customers/{id}, POST /customers/{id}/accounts, GET /customers/{id}/accounts, GET /accounts/{id}, POST /accounts/{id}/deposits, POST /accounts/{id}/withdrawals, POST /transfers.
Layer 3 Validator Layer (src/validators/)
  • Customer Validator (customer.validator.js): Validates fullName (non-empty string), email (RFC 5322 regex pattern). Validates customerId path parameter.
  • Account Validator (account.validator.js): Validates type enum (CHECKING, SAVINGS), currency enum (CAD, USD), and initialBalance ($ge 0$, finite, $le 2$ decimal places).
  • Transaction Validator (transaction.validator.js): Validates positive finite amounts ($le 2$ decimal places to prevent IEEE-754 precision bugs), currencies, and disallows self-transfers (fromAccountId !== toAccountId).
  • Exported Functions: All functions are pure, exported, and unit-tested in isolation in test/validators.test.js.
Layer 4 Service Layer (src/services/)
  • Customer Service (customer.service.js): Generates cust_${uuidv4()}, assigns default status ACTIVE and ISO timestamp. Retrieves customer by ID; throws HttpError.notFound if not found.
  • Account Service (account.service.js): Validates customer existence before account creation. Assigns acct_${uuidv4()} and status OPEN. For listing accounts, verifies customer existence first to ensure invalid IDs return 404 rather than ambiguous empty arrays.
  • Transaction Service (transaction.service.js): Enforces financial rules: checks account existence, checks accounts are OPEN, checks currency matching, enforces overdraft prevention (balance >= amount, throws 409 Conflict if insufficient), and coordinates atomic transfer transactions.
Layer 5 Repository Layer (src/repositories/)
  • Customer Repository (customer.repository.js): Encapsulates findById (GetCommand), create (PutCommand), and delete (DeleteCommand).
  • Account Repository (account.repository.js):
    • Point lookups via GetCommand on partition key accountId ($O(1)$).
    • Customer accounts query via Global Secondary Index (CustomerIdIndex) with QueryCommand ($O(1)$ partition lookup, zero table Scans).
    • Balance increments/decrements via atomic UpdateCommand with ConditionExpression.
    • Cross-account transfers via DynamoDB ACID TransactWriteCommand (all-or-nothing debit and credit, zero risk of partial failure, with local emulator fallback).

5. How to Present this in Technical Interviews

1. Pitching the Architecture
"I built a clean 4-tier architecture following Domain-Driven Design and SOLID principles: Handlers act purely as HTTP controllers; Validators enforce contract boundaries and data formats; Services encapsulate banking business rules; and Repositories isolate DynamoDB operations. Additionally, all endpoints are guarded by a JWT Bearer authentication middleware."
2. Why Separate Services & Repositories?
"Separation of concerns is critical in financial applications. Keeping business rules (such as overdraft checks, currency compatibility, and account status validation) inside Services makes them testable in pure memory without mocking database calls. Repositories isolate AWS SDK specifics (like GSI Query parameters, ConditionExpressions, and TransactWriteItems), allowing database optimizations or migrations without altering business rules."
3. Why Dedicated Validators?
"Dedicated validators provide a fail-fast boundary right at the controller entry. They validate types, regular expressions, and decimal precision before any domain service or database connection is invoked, preventing malformed data from ever touching business logic."
